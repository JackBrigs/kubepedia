# /kubepedia — ответ из базы, а не из памяти модели

База — источник истины. Она версионно-точна и привязана к тегам Kubespray; собственные
воспоминания модели о версиях, дефолтах и переменных **не являются ответом**. Если в базе
чего-то нет — так и сказать.

Все команды выполняются из корня проекта. Зависимостей нет: Python 3 + PyYAML.

## Шаг 1 — определить тип вопроса и дёрнуть нужный инструмент

| Вопрос выглядит так | Команда |
|---|---|
| текст ошибки, симптом, «почему не поднимается» | `python3 scripts/ask.py "<строка ошибки>"` |
| **вставлен сырой вывод** (`describe`, логи пода, `journalctl`) | сохранить в файл и `python3 scripts/ask.py - < файл` |
| «какая версия X в v2.29.0», «что поедет при апгрейде версии» | `python3 scripts/versions_lookup.py <компонент>` |
| «что изменится при переходе A → B» | `python3 scripts/upgrade_report.py --from vA --to vB [--inventory <dir>]` |
| «что сломает мой inventory при переходе» | `python3 scripts/upgrade_diff.py --from vA --to vB --inventory <dir>` |
| «всё ли доехало после апгрейда» | `python3 scripts/post_check.py --version vX --print-gather`, затем `--facts facts.json` |
| «что зависит от X / что сломается, если менять X» | `python3 scripts/impact.py <ID или имя>` |
| «есть ли CVE на нашей версии» | `python3 scripts/cve_sweep.py [компонент]` |
| «база ещё актуальна?» | `python3 scripts/freshness.py` |

Если вопрос не ложится ни в одну строку — начинать с `ask.py`: он ищет по алиасам, заголовкам,
телу и тегам и почти всегда приводит в нужный раздел.

## Шаг 2 — ответить

**Версия — фильтр, а не примечание.** Если в вопросе есть тег Kubespray или минор Kubernetes,
ответ обязан относиться именно к ним. Если версия не названа — спросить или явно сказать, для
какого диапазона верен ответ. Факт без версии в этом проекте считается непроверенным.

**Отвечать фактами, а не отсылками.** Не «смотри документ про conntrack», а сами цифры, имена
переменных, команды и порядок действий. Отсылка допустима только как «подробнее», после ответа.

**Формат операционного ответа:** причина (одним абзацем) → проверка и команды → влияние на сервис
(простой, рестарты, что переживёт прогон) → чем это чинится насовсем. Без развёрнутой процедуры,
если её не просили.

**Прогоны Kubespray — в терминах AWX.** Владелец гоняет через AWX, поэтому давать поля job
template: playbook, Job Tags, Limit, Extra Variables, Privilege Escalation — а не строки
`ansible-playbook`. Ловушки, которые не переживают перевод (интерактивные паузы `reset.yml` и
`remove-node.yml`, `upgrade_node_confirm`, выключенный become), называть сразу.

**Наружу не показывать внутренние идентификаторы документов.** Пользователь видит заголовки и
факты, а не `TROUBLE-*`, `CONCEPT-*`, `VARIABLE-*`.

**Язык — русский, живой.** Вывод скриптов — сырьё, а не ответ: пересказать своими словами,
сохранив числа и имена. Особенно это касается отчёта об апгрейде: он длинный, из него нужно
достать главное — что ломается, что закрывается, что делать — и только потом детали.

## Шаг 3 — если ответа нет

Сказать прямо: «в базе разбора на это нет». Дальше — на выбор пользователя:

1. **Исследовать по источникам.** Только по тегнутому исходнику (`kubespray-src`, `src-cache/`,
   апстрим-репозиторий на нужном теге) или официальной документации нужной версии. Никаких
   «обычно бывает так».
2. **Внести в базу.** Оформить разбор по контракту проекта (`standards/kds.md`), с источниками,
   версионным конвертом и алиасами из реальных строк ошибок, прогнать
   `generate_index.py` → `validate_kds.py`, закоммитить отдельным изменением.

Пробел — это результат, а не неудача: он показывает, где базу надо растить.

## Границы

- Не выдумывать версии, переменные, CVE и поведение. Сомнение проверяется по исходнику на теге —
  или проговаривается вслух.
- Не показывать пути к файлам базы вместо ответа.
- Инструменты только читают. Ничего в кластере не менять; команды, меняющие состояние, —
  предлагать пользователю, а не выполнять.
- Отчёты и проверки не выдумывать по памяти: цифры берутся из вывода инструментов.
